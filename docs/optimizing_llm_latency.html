The request path

Six phases, one thread of control

Configuration D. Bars share a single scale from 0 to 6.7 seconds. Stages under 100 ms are drawn as a hairline because that is how big they are.

Stage & what runs
0 s 2 s 4 s 6.7 s

1 · In the browser

not on the clock
  • Speech in via useOfflineSpeechToText, or the student types
  • POST /api/chat/stream opens an SSE connection api.ts
timer starts at the first byte of the request

2 · Retrieval

1.4%
  • Session fetched, question appended, turn_id minted, start frame sent chat.py:_stream_events
  • Question embedded — prefixed search_query:, one HTTP call to Ollama embeddings.py:embed_query
  • Flat KNN over chunk_vectors, filtered to grade + subject store.py:search
  • Hits beyond distance 0.42 dropped; retry across subjects if none survive
  • Top 2 packed to a 1,200-char budget, best-first retrieval.py:build_context_block
91 ms — embed ~85 ms · search 3–8 ms · gate <1 ms

3 · Prompt assembly

free, but decisive
  • Persona and style rule, then the preamble, then the excerpts tutor.py:build_system_prompt
  • Last 2 history messages appended, then the question config.py: max_history_messages
<1 ms of work that sets the size of the next 3.7 seconds

4 · Prefill

54.6%
  • Ollama reads the prompt before emitting anything — 325 tokens on average
  • A median 86 tokens now hit the KV cache; on a repeated leading excerpt, up to 309
  • The rest at 18.2 ms each — batched matrix work, compute-bound
3,667 ms — was 11,608 ms before the prompt was reordered

5 · Generation

40.5%
  • First token crosses the SSE hop and paints in 6 ms
  • 46 tokens at 16.9/s — matrix-vector work, memory-bandwidth-bound
  • Was 128 tokens. The shorter style rule, not the machine, made this fall
2,720 ms — threads do not move this; it scales with memory bandwidth

6 · Speech out

overlapped
  • drainSentences pulls complete sentences off the growing buffer
  • First speakable phrase ready ~250 ms after the first token
  • Piper WASM synthesises it in ~950 ms — one pass per sentence
  • Student hears audio at 5.4 s, while the model is still decoding
runs inside phase 5
Playback then continues past the last token — that is the answer being spoken aloud, not compute.

A sliding window can never be cached: dropping a message off the front shifts every token behind it.

Why this flip worked when the last one failed

The reverted attempt moved the excerpts onto the user message, below the whole conversation. Against 12 pronoun-only follow-ups (“why does it get bigger?”), that dropped answering-from-the-conversation from 11/12 to 5/12 — a weak retrieval hit adjacent to the question overrides the dialogue. This change keeps the excerpts inside the system message, above the history; only the persona moved. What made it viable is that the style rule is now short enough to survive being read before a few hundred words of textbook. That claim is not yet re-measured — the 12-follow-up eval has not been run against this layout.

The whole device in one equation

Latency here is arithmetic, not tuning

turn_ms = (prompt_tokens − cached_prefix) × 18.2 ← prefill, compute-bound + completion_tokens ÷ 15.6 × 1000 ← generation, bandwidth-bound + retrieval_ms (~91) + overhead (~350) A old prompt 627 in / 128 out · ~0 cached → 20.1 s D new prompt 325 in / 46 out · 86 cached → 6.7 s

This is why OLLAMA_NUM_THREAD=4 changed nothing. The device is not thread-starved: 55 tokens/s of prefill is roughly what a four-core laptop should manage on a 1.5B Q4 model. The 3.5× prefill-to-generation ratio, against 8.2× on the reference box, describes a machine that is bandwidth-rich and compute-poor. The only way to spend less time is to feed it fewer tokens — which is exactly what the prompt rewrite did.

Two changes are riding together, and only one is a latency change

Answers fell from 638 characters to 223 — because the socratic rule was rewritten from “at most 3 sentences … your reply MUST end with a question mark” to “at most 3-5 sentences - one small hint”. That is 5.5 of the 13.4 seconds saved, and it is a pedagogy decision, not a free win. Worth confirming a 223-character answer is still the tutoring you want. One loose end: needs_socratic_retry still tests whether the reply ends in a question mark, which the prompt no longer asks for — and it only runs on the non-streaming endpoint, so it never fires for the UI anyway.

The 0.5b model swap is no longer needed for latency. First token is at 4.1 s and first audio at 5.4 s, inside the target, on the 1.5b model — which means the eval harness that swap was blocked on can be spent on the retrieval quality question instead.
